- [x] D8 (security round 1, default): Should the default `[autopilot] guards` also include `[review] sensitive`? Assuming yes. The spec's default is policy doc, review doc and `[review] irreversible`, so a change touching a sensitive path lands and is pushed unattended, and only the risk budget counts it (+3). In this repo that list covers `.github/workflows/`, `closing.py`, `landing.py` and `autopilot.py` itself. The plugin is read in place from the main checkout, so `run_step()` runs `FACTORY_SCRIPT` fresh from there. A change that autopilot lands to those files therefore changes the code that runs the rest of the same run, even though its config was fixed at `--begin`. → decided: the assumed default, confirmed
  - OPTION: add `[review] sensitive` to the default guards — no unattended landing or push of CI, auth or the factory's own lock and hold code; holds more changes, and a host can narrow `guards` explicitly
  - OPTION: keep the spec's defaults — more changes land; a workflow or guard-code edit can be pushed with no person, only weighed in the budget
  - OPTION: guard sensitive paths only when `git.push` is on — local-only landings can still be reverted; mixes two rules
  - WHY: the intent says autopilot never lands a change that breaks a guard, and can't loosen the run it's in. Sensitive paths are where a weakening is exploitable, and in this repo they include the run's own code.
- [x] D9 (security round 1, default): Should a seed carrying an `Issue:` line (public issue text) be a candidate only when named in `--seeds`? Assuming yes. `open_seed()` / `opened_intent()` never write the `closes:` line `/sdlc:intent` adds for such a seed. As a result `land_signals()`'s `issue` signal never fires for autopilot's changes, R26's `issue` weight is never counted, and the issue is never closed. Under autopilot, text an outsider wrote reaches an intent, a spec and a build that nobody reads before it lands and is pushed. → decided: the assumed default, confirmed
  - OPTION: only when named in `--seeds`, and always carry `closes:` — outsider-written text is built unattended only by explicit choice, and the risk signal and issue close work again; fewer candidates
  - OPTION: carry `closes:` only, keep them as candidates — the budget counts them; nobody reads the issue text before it is built
  - OPTION: never take them under autopilot — safest; leaves triaged bugs for the person
  - WHY: the `issue` signal exists so a person sees public-issue changes before they land. Dropping `closes:` makes that signal silently disappear.
- [x] D10 (security round 3, default): Treat `AUTOPILOT_RUN_ENV` as protection against *inheriting* the marker by accident. It is not a boundary against a process that sets the marker on purpose, and the docs should say so. `autopilot_running()` (factory.py:3465) checks two things: the env names `<git-common-dir>/sdlc-factory-autopilot-run.lock`, and some process holds that lock. That path is public and predictable. So while the loop runs, any process running as the same user can set the variable itself and pass `--by autopilot`. That includes a builder session started as a loop step, whose `Bash` runs with `--permission-mode auto`. For example, seed text could tell it to run `SDLC_FACTORY_AUTOPILOT_RUN=$(git rev-parse --git-common-dir)/sdlc-factory-autopilot-run.lock factory.py answer NNN Dk --by autopilot`. Spec R2 defines the check exactly this way, and earlier rounds passed that design. I'm raising it as a decision, not a CHANGE. A secret token would not close it either: a same-user process can read any file the loop can. → decided: the assumed default, confirmed
  - OPTION: accept and document — say in AGENTS.md and the factory README that `--by autopilot` stops accidental inheritance, not a same-user process that sets the marker deliberately. The real limit on a misled builder is its permissions and sandbox. Costs nothing, but leaves the risk open.
  - OPTION: sandbox the builder's `Bash` during autopilot (Claude Code's sandbox, or a deny rule on `factory.py` and on setting `SDLC_FACTORY_*`) — actually closes it, but deny rules are best-effort and could block legitimate builder commands.
  - OPTION: make the loop's own steps check the ledger themselves — for example, before `land` the loop checks that each `→ decided by autopilot:` line matches a call recorded in `AUTOPILOT_STATE`, and stops if not. A forged call is then caught before it lands. It costs code in `autopilot.py`, and the state file can be forged the same way.
  - WHY: no in-process check can tell a deliberate same-user process from the loop's child. Writing the limit down keeps the docs from claiming a boundary the code doesn't have.
